# 需求处理工作流

> 所有回覆必須使用繁體中文。

---

## 启动判断（原则式）

收到用户需求时，先评估是否需要走本流程。判断原则：

**需要走流程** — 满足以下任一条件：
- 涉及多文件变动
- 会改变现有行为或架构
- 需求存在模糊空间（未指定具体做法、范围不明确）
- 跨模组影响

**不需要走流程** — 直接执行即可：
- 明确的小 bug 修复（用户已指出具体问题和位置）
- 单文件简单改动（改值、加 log、调样式）
- 用户已给出完整具体指令的操作
- 纯查询、研究、解释代码

> **拿不准时，走流程。** 多确认一次的成本远低于返工。

---

## 标准流程

### Phase 1：需求厘清

收到需求后，**不要立刻动手**。先做：

1. **复述理解** — 用自己的话简要说明你对需求的理解
2. **主动提问** — 把不确定、有歧义、或需要用户决策的点列出来问
3. **标注假设** — 如果有些地方你做了合理假设，明确告知用户

输出格式：

```
## 我的理解
（复述需求）

## 需要确认的问题
1. ...
2. ...

## 我的假设（如有）
- ...
```

### Phase 2：认知同步

根据用户回覆，确认双方对以下达成共识：
- **范围**：要改什么、不改什么
- **做法**：技术方案 / 实现思路
- **影响**：会影响哪些现有功能或文件

如果有新的疑问，继续在这个阶段厘清，直到没有模糊点。

### Phase 2.5：需求再确认

认知同步过程中，讨论可能导致需求发生变化（范围扩大、缩小、或方向调整）。
在进入计划阶段前，**必须再次确认最终需求**：

- 简要列出经过讨论后的最终需求（与最初可能已不同）
- 明确标注与原始需求的差异（如有）
- 取得用户确认后才进入 Phase 3

### Phase 3：制定计划

调用 `EnterPlanMode` 工具进入 Plan Mode，建立具体的实作步骤：
- 列出要修改/新增的文件
- 说明每个文件的变动内容
- 标注风险点或需要注意的地方

计划呈现完毕后，调用 `ExitPlanMode` 工具结束 Plan Mode。这会产生标准的「Plan to implement」确认界面，让用户选择：
- 确认并开始实作
- 清除上下文后实作（context 使用率高时）
- 自动接受所有编辑（shift+tab）

> **注意：** 不要在 Phase 3 自行开始实作，必须等待用户通过确认界面触发 Phase 4。

### Phase 4：实作执行

计划确认后，按步骤实作。实作过程中如果发现计划外的问题，**暂停并告知用户**，而非自行决定。

---

## 注意事项

- 流程可以简化但不跳过：小型需求的 Phase 1 和 Phase 2 可以合并，但至少要有一次确认
- 不要把流程本身变成负担：如果需求非常清晰只是稍微超出"小事"范围，简短确认即可
- 用户明确说"直接做"时，尊重用户意愿，跳过流程
