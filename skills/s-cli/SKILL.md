# s-cli

Follow `<slot-fe-client-root>/.codex/agents/s-cli-agent/AGENT.md`.

## Browser access

When the workflow needs to open, inspect, or interact with a web page, use the
`chrome_devtools` MCP exclusively. Do not invoke the `browser` or
`browser:control-in-app-browser` skill, or substitute another browser-control wrapper. This
does not replace Cocos MCP for editor/scene/console inspection, nor direct HTTP checks for
server-contract evidence. The `s_init` planning modes remain prohibited from browsing the
competitor URL. If `chrome_devtools` is unavailable, preserve the non-browser evidence and
report `NEEDS_CHROME_DEVTOOLS` for the blocked browser evidence rather than changing tools.

For every permitted Chrome MCP run, call `list_pages` before opening the target and record the
baseline page IDs. Create a task-owned page, preferably in a task-specific isolated context;
do not repurpose or later close an unrelated baseline page. Before loading any target that may
play audio, mute the dedicated Chrome MCP browser instance through a supported instance-level
launch/configuration or MCP mechanism and verify it. HTML media-element muting alone is not
sufficient because the game may use WebAudio. If mute cannot be applied or verified, return
`NEEDS_CHROME_MUTE` before navigation or interaction.

Track every page and popup created by the task. In a cleanup-safe `finally` path for success,
failure, timeout, and blocked exits, stop any active trace and save required evidence, close
all task-owned pages in reverse creation order with `close_page`, then close a dedicated
task-owned Chrome instance when an ownership-specific shutdown is available. Verify cleanup
with `list_pages`. Never close baseline pages or terminate Chrome by broad process name. If the
last task-owned page or instance cannot be closed, return `CHROME_CLEANUP_FAILED` with its
identity and do not claim browser acceptance or cleanup success.

## s-init planning contribution

Only when `s_init` explicitly dispatches `s_cli` for `doc/project_plan.md`, replace the normal implementation loop with a read-only planning contribution. Resolve `replicationId` from the target `slot-fe-{slug}` project name, then inspect its `doc/js_scripts`, `doc/project_info.md`, current target client, any redacted runtime evidence saved by `s_init`, and `assets/resources/{replicationId}_res` only when that root contains ordinary files and no reparse point anywhere in its tree. Keep a differing legacy provider/wire `gameId` explicit as `metadataGameId`. If the resource root is missing or empty, return a partial contribution from the remaining evidence plus `NEEDS_LOCAL_REFERENCE`; if it contains a reparse point, treat it as an invalid local reference and do not inspect it. Do not block `s_init` from producing `DRAFT_EVIDENCE_GATED` for a merely missing or empty root, and do not claim resource-backed behavior without valid local files. Do not browse the competitor URL, initialize files, create `doc/s_cli/**`, write a plan, or modify code/resources. `doc/project_plan.md` is a roadmap and must never be validated or executed as a version 2 `plan.json`. All normal `s_cli` invocations continue with the rules below.

## s-init execution mode

Only an explicit `s_init execution` dispatch inside the client goal enables this mode. Require the server goal's completed state and accepted handoff below `doc/s_init/server/`, matching roadmap and client detailed-plan hashes/baselines, a current `doc/s_init/client/detailed-replication-plan.md` with `detailedPlanState: READY_FOR_EXECUTION`, `SIMULATOR_PASS`, and `LOCAL_RUNTIME_PASS`. If the accepted server is unavailable, return `NEEDS_SERVER_RECOVERY`; never start, stop, reconfigure, or modify it from `s_cli`.

Execute two formal `s_cli` tasks in order; each still needs its own target-local task directory, root-cause evidence, version 2 `plan.json`, validation, acceptance, and result:

Determine the active build profile and `GameConfig -> gameConfig.json -> Host` override order; do not rewrite historical profiles or donor-like class/node names without a proven consumer migration.

Treat `doc/project_plan.md` and `doc/s_init/client/detailed-replication-plan.md` only as planning inputs, then run the normal Reel/Spin/SlotReel `ROOT_CAUSE -> PLAN -> EXECUTE -> ACCEPT -> REPORT` workflow. Save or recapture the accepted deterministic server response below this client's `doc/s_cli/**` tree and use that local artifact for `serverDataCheck`; a runner path or server-side document is not a valid plan evidence path.

Do not begin Reel work until the identity task passes residue classification, config parsing, Scene/meta/reference checks, relevant static/build checks, and a Cocos active-project/launch-scene smoke check. Return `IDENTITY_MAPPING_CONFLICT`, `NEEDS_ACTIVE_BUILD_PROFILE`, `NEEDS_PROTOCOL_EVIDENCE`, or `SERIALIZED_IDENTITY_UNRESOLVED` rather than guessing an identity owner. Do not complete the client goal until Reel acceptance and the required target fixture replay pass. Keep build, visual, deployment, and cross-end evidence as separate results.
